# ADR：书封存放方式——继续直接引用上游图床，补三道保险，转存只作触发式预案（待办 B-37）

## 1. 决定（白话版）

1. **书封继续直接引用上游图床，不下载、不转存。** 页面上的封面图地址仍然是上游给的那一条，浏览器直接去上游取。
2. **给这个做法补三道保险**，因为直链意味着上游图床出问题时我们会跟着一起坏：
   - 失效自愈：发现某本书的封面地址失效后，能自动从上游重新取到新地址并修正；
   - 可用性监控：定期检查封面是不是还能打开，坏了要有人知道；
   - 破图兜底：真有一张图加载不出来时，页面显示统一的"无封面"占位，而不是浏览器自带的破图图标。
3. **转存到本机只作预案，触发了才做。** 触发条件写死在第 3 节，没触发就不做。
4. **先做阶段 0**：与存放方式无关、无论将来转不转存都该修的前端问题（首屏加载优先级、破图兜底、分享图卡片口径）。

## 2. 为什么这样定（只读实测依据）

以下都是只读核对得到的事实，没有改动任何生产数据。

- **规模与形态**：已发布 28,745 本，书封全部是 cdreader 图床上的固定路径——没有签名、没有查询串、没有防盗链。也就是说今天"直接引用"在技术上是畅通的。
- **上游自身的可靠性**：上游图床是 Akamai 加腾讯云 COS，且 COS 开了版本管理。这类基础设施本身不容易无故丢图，主要风险来自上游**主动改变做法**（开防盗链、换域名、下架）。
- **图本身很小**：书封是 250×350 的 JPEG，平均约 18KB。转成 WebP 只省约 15%，没有"为了省流量而转存"的理由。
- **转存的代价**：本地化需要磁盘约 0.5GB（只算已发布）到 1.9GB（算全部书目）。磁盘不是问题，问题在两点：一是要为此维护下载、校验、失效重取的整套流程；二是生产 nginx 的页面限流是全站共用的（并发 10、每秒 12 个请求），**转存之后图片流量会挤占页面配额，必须为图片单开一个 location**，不能沿用页面的限流。
- **同构风险已经在短剧站发生过**：CPS 的畅读渠道有 2,933 部剧，因为上游换了 CDN 域名，而剧的封面字段只在"建剧"那一刻写一次、之后不再更新，于是静默破图，约 2,331 篇已发布页面受影响。海阅的封面地址同样是建书时写入、合同上只补空不覆盖（见第 3 节阶段 1），结构上与那次事故同构——所以"失效自愈"和"可用性监控"不是可选项，而是直链方案成立的前提。

**所以没有选择"现在就转存"**：直链今天没有问题，转存要新增一整条运维链路和 nginx 配置；而真正的风险（上游改变做法）靠监控与自愈就能发现并兜住，只有当上游真的把路封死时，转存才变成必须。

## 3. 分阶段

### 阶段 0：本次内容（已实现，待合入）

与存放方式无关、现在就该修的部分：

- **破图兜底**：封面加载失败时显示现有的"无封面"占位，不露浏览器自带的破图图标。包含一种容易漏的情形——服务端渲染出来的图片在页面脚本接管之前就已经加载失败了，浏览器不会再补发错误事件，所以挂载时还要主动检查一次。
- **首屏优先级**：详情页主封面、首页轮播的初始项设为高优先级加载；其余封面保持懒加载。
- **轮播背景按需设置**：首页轮播的模糊背景此前对所有项无条件设置，页面一打开就把全部轮播封面请求一遍。现在首次渲染只给初始项设置，下一项在当前项稳定约 2 秒后预备，轮到谁谁必设，设过就保留不再摘掉（避免淡入时闪烁）。
- **图床预连接**：详情页对该书封面所在的图床、首页对初始轮播项封面所在的图床各声明一次预连接，让握手提前。只认 https 绝对地址，按图床去重。
- **分享图卡片口径**：见第 5 节。

阶段 0 **没有做**的：不下载、不转存、不监控、不改数据库、不动博客模板、不动列表卡片等其他用到封面的地方。

### 阶段 1：监控、自愈与发布前白名单（未开工）

- **可用性监控**：每天抽样检查，每周全量检查。
- **失效自愈**：发现失效后从上游重新取封面地址并修正。**这一项需要先改一条合同**：`db:public:novel:novel_canonical_fill_only_contract` 目前把封面地址定为"只补空、不覆盖"，自愈要给 `cover_url` 开一个"仅在确认失效时才允许修复"的例外。**该例外尚待 Owner 拍板，未拍板前不得实现。**
- **发布前图床白名单**：发布一本书之前，校验它的封面地址属于已知的可信图床，防止把来路不明的地址发布出去。

### 阶段 2：触发式转存（预案，没触发就不做）

只有出现下列任一情形才启动：

1. 上游开了防盗链或签名；
2. 整个图床域名失效，而且自愈救不回来；
3. 合同要求我们自行托管封面；
4. 决定做带品牌的 1200×630 分享图（那时书封本来就要经过我们自己的处理环节）。

做的时候必须为图片单开 nginx location（原因见第 2 节）。

## 4. 待向上游确认的问题

这些是**还没有答案**的问题，答案会影响阶段 1、2 的取舍，需要 Owner 或渠道对接人去问：

1. 上游是否允许我们**直链引用**、**保存副本**、**改格式**（例如转 WebP）？
2. 一本书下架之后，上游要求我们**多久之内撤掉封面**？
3. 上游有没有**更高分辨率**的封面？目前 250×350 偏小，分享图和 Retina 屏上都不够清晰。
4. 3,576 本**英语草稿**的封面在阿里云的 `plotread/temp/` 路径下，名字带 temp——这些封面**会不会被上游清理**？如果会，这批书一旦发布就会破图。

## 5. 本 ADR 对既有 ADR 的修订：分享图卡片类型

被修订的是 [ADR-PUBLIC-CUTOVER-20261007-PREREQUISITES.md](ADR-PUBLIC-CUTOVER-20261007-PREREQUISITES.md)「Owner 追加裁决：分享图口径更正」一节里**卡片类型的细节**。
旧裁决的原文**不改**，它讲的是"哪个域名、是否 HTTPS、有书封时用书封、无书封时用站点默认图"，这些都仍然成立；旧裁决没有规定卡片类型，本节补上，并明确**书封作分享图时用小图卡片**。

**问题**：此前所有页面模板都把分享图声明成宽 1200、高 630，并把 `twitter:card` 设为 `summary_large_image`。但书封实际是 250×350，宽度低于 X 大图卡片要求的最小宽度 300。等于对平台谎报了尺寸：平台要么不给大图卡片，要么把竖封面拉伸裁切。

**新口径**（以"最终选中的是哪一张图"为准，判定只在一个共享函数里，各模板统一调用）：

| 最终分享图 | `twitter:card` | `og:image` 的尺寸声明 |
| --- | --- | --- |
| 站点默认图（`public/brand/og-default.png`，实测 1200×630） | `summary_large_image` | 声明宽 1200、高 630 |
| 书封 | `summary`（小图卡片） | **不声明**宽高 |

适用页面：小说页、章节页（书封优先、默认图兜底），以及首页、浏览页、分类页（站点默认图优先，只有默认图缺失时才拿"列表第一本书"的封面兜底）。这三个列表类页面此前把"默认图或第一本书封"合并成一个值再交给模板，模板分不清最终选的是哪一种，现在改为两个值分开传。

**不在本次范围**：博客页。博客封面是运营上传的，尺寸未知，保持旧口径，另行处理。JSON-LD 里的 `image` 字段不变。

**为什么暂不做带品牌的 1200×630 分享图**：那需要书封先经过我们自己的处理环节，等价于启动阶段 2，所以列为阶段 2 的触发条件之一。

## 附录 A：术语表

| 词 | 含义 |
| --- | --- |
| 直链 / 直接引用 | 页面上封面图的地址就是上游图床的地址，浏览器直接去上游取，本站不经手 |
| 转存 | 把封面图下载到本机，由本站自己的域名提供 |
| 失效自愈 | 发现封面地址失效后，自动向上游重新取到新地址并写回 |
| 预连接 | 在图片真正开始下载之前，提前与图床完成域名解析与加密握手 |
| 站点默认图 | 后台"站点设置"里的默认分享图，目前是 `public/brand/og-default.png` |
| 小图卡片 / 大图卡片 | X（Twitter）分享卡片的两种版式，对应 `summary` 与 `summary_large_image` |
