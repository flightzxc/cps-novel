# ADR-B41：IndexNow 批量推送与存量回填，对齐 CPS

- 状态：已实施（v0.5.15）。Owner 于 2026-10-10 拍板：方案第一节 8 项全部按推荐，另有两处修改、一条补充和一道额外的配置检查（方案第〇.五节）；主控评审的 8 点增补同日经 Owner 批准（开发单第 7 节）。
- 方案：`方案_B41_IndexNow批量推送与存量回填_对齐CPS_2026-10-10.md`；施工单：`开发单_Sonnet_B41_IndexNow批量推送与回填_2026-10-10.md`。
- 约束：公开网址冻结期间不改任何网址、跳转、canonical、hreflang、站点地图；本决定零数据库迁移、零授权变更、零新环境变量。
- 取代：`ADR-WO6-INDEXNOW-LIGHT-FAIRNESS.md` 中"本单不移植其（CPS）协议""每个投递条目只提交一个 URL""定时 handler 显式限制 200 条候选"这几句。该 ADR 的其余部分（分钟扫描、轻量通道公平轮转、双闸）继续有效。

## 一、背景（业务视角）

生产站点有约 3.08 万篇已发布的小说文章，IndexNow 从未开过。要让搜索引擎知道这些网址，海阅原来的做法有四个缺陷：

1. 每次请求只推 1 个网址，3 万个网址就是 3 万次请求、约 2.5 小时纯请求时间；CPS 一次推最多 500 个。
2. 站点设置里的 IndexNow 配置缺失时，扫描仍然每分钟建任务，任务一到就跳过，空转。
3. 回填只看 id 最小的前 5,000 篇文章，其余的永远看不到。
4. 回填的"停止条件"只看当前这一页的记录，前面批次出的问题拦不住后面。

CPS 已有批量推送和回填的实战记录（生产 10-04 两分钟推了 6,693 个网址，14 次请求，全部 200）。本决定把海阅对齐到 CPS，并在两处做了 CPS 没有的加固：遇到 400/403/422 整体暂停（熔断），遇到 429 全局等待。

## 二、决定

### 1. 批量：一批最多 500 个网址，一次 HTTP 请求

- 一个批量投递任务只有一个条目，条目对应一批（不超过 500 条出站记录）和一次请求。先进先出，按创建时间排序。
- 保留海阅更严的机制：通用任务租约与 fencing、轻量通道里投递组与其它任务轮流执行、四个开关、写闸登记、主通道禁止 IndexNow 类型。
- 领取和写回都是一个事务：领取事务里逐行带条件更新为"处理中"并一次写入整批的尝试记录；HTTP 之后，尝试记录与出站记录的结果在同一个事务里写回。请求本身用 10 秒超时与任务租约信号二者之一中止。

### 2. 发布只记录、不建任务；由每分钟扫描统一打包

- 发布（按钮、后台批量发布）和人工释放只写出站记录，不再为每篇建任务。
- 每分钟的扫描任务按固定顺序检查：开关 → 崩溃恢复 → 配置是否齐全 → 配置的域名是否等于站点域名 → 熔断 → 429 等待 → 有没有到期记录 → 有没有在途批量任务。任何一步不满足就不建任务，并在结果里写明原因；全部满足才建一个批量任务。
- 同一时间只有一个在途批量任务，由数据库唯一索引保证（`generic_task_active_scope_uidx`，范围哈希固定为 `sha256("indexnow_delivery:batch")`）。建任务用"撞唯一键就什么都不做"的写法，不会在并发下让扫描事务失败。
- 没有积压时，一篇文章从发布到被推出大约 1 分钟；这是常态，不是硬保证。有积压时吞吐上限是每分钟 500 个网址。

### 3. 熔断：400、403、422 整体暂停，人工恢复

- 这三种状态码意味着整批或整个配置有问题，不是某一个网址的问题（批量之前，一次 403 只影响 1 个网址，批量后一次就是 500 个）。400 与 403、422 同等对待。
- 出问题的那一批退回"待重试"并立即到期，但**熔断打开期间不会被领取**；它们不判永久失败，否则恢复后"回填按文章判重"会让这 500 个网址再也不被推。已用尽重试次数的转死信。
- 熔断状态不新建表，用 `operation_audit` 上的**控制事件流**表示，见下面第四节。
- 恢复只有一个入口：`scripts/indexnow-delivery-resume.ts`，必须给出操作人和原因，写一条恢复审计；状态里有在途请求时拒绝。恢复后，被挡住的那一批会**单独**重推，不与新记录混在一起。

### 4. 控制事件流（零迁移的熔断与等待状态）

事件都写在 `operation_audit`，`entity_type = "indexnow_delivery"`：

| 流（`entity_id`） | 事件（`action`） | 谁写 | 何时写 |
|---|---|---|---|
| `breaker` | `indexnow.delivery.breaker_trip` | worker | 写回事务里，HTTP 状态是 400/403/422 |
| `breaker` | `indexnow.delivery.breaker_resume` | 恢复命令（管理员） | 人工恢复 |
| `rate_limit` | `indexnow.delivery.rate_limited` | worker | 写回事务里，HTTP 状态是 429 |
| `bisect` | `indexnow.delivery.bisect` | worker | 拆半结束 |

读状态的规则（状态是"已提交事件"的纯函数）：

- **熔断**：`breaker` 流里 id 最大的事件是 trip 就是打开；是 resume 或者没有事件就是关闭。
- **429 等待**：`rate_limit` 流里 id 最大的事件，它的 `waitUntil` 大于数据库当前时间，就在等待中。
- **同一批再次失败**：当前 trip 事件里的 `heldRetry`（它那一批是不是恢复后单独重推的被挡批次）。
- 一条 SQL、同一个快照、数据库时钟，三项一起读出。**读取方式有硬性写法要求**：每条流先用固定的 `entity_type`/`entity_id` 圈出（`WITH … AS MATERIALIZED`，命中现有索引 `operation_audit_entity_created_idx`），再在这一小撮行里按 `id DESC` 取最新一条；禁止对全表写 `ORDER BY id DESC LIMIT 1`，也禁止按 `created_at` 排序。真实库用例在 ≥ 75 万行 `operation_audit` 上用 `EXPLAIN (ANALYZE)` 断言命中该索引、没有对该表的顺序扫描、没有沿主键的扫描、执行时间小于 50 毫秒。

评审提出的四个问题的答案：

1. **怎么判断熔断已被恢复覆盖？** 同一条流里，resume 事件的 id 大于 trip 事件的 id。`created_at` 只用来显示：它是事务开始时间，不等于提交顺序（真实库用例 29c 专门构造了"较早开始的事务较晚提交"的反例）。
2. **恢复期间又出现新失败怎么算？** 新失败写一条新的 trip 事件，id 一定大于 resume，所以熔断重新打开。
3. **多个 worker 同时读，状态是否一致？** 写 trip / rate_limited / resume 事件的事务，以及领取事务（含拆半的子请求），开头都先执行 `pg_advisory_xact_lock(50241, 1)`（命名空间 50241，已确认未被占用；已占用的是 50210、50211、50212、50330）。同一条流里事件 id 顺序就等于提交顺序。读的人可能看到稍旧一点的状态，但真正要采取的动作（领取、恢复）都在锁内用同一套规则重新判断，所以不会依据过时的读数行动。
4. **429 的截止时间从哪里来？** 只来自事件本身：`waitUntil = 数据库时钟 + max(Retry-After, 5 分钟)`，写事件时算好。不借用任何记录的 `nextAttemptAt`，所以取消或重新领取那批记录都不会改变它（用例 32）。

恢复命令在锁内检查：最新事件不是 trip 返回 `breaker_not_open`；存在在途请求（尝试记录 `started` 且 `request_at` 距现在不超过 35 分钟）返回 `in_flight_requests_present`；同一个 request id 重放返回 `request_id_reused`。

旧数据：v0.5.14 单条时代如果有过 4xx 的推送记录，它们没有对应的控制事件，不会触发熔断。

### 5. 429：全局等待

收到 429，本批按原有退避规则重试，同时写 rate_limited 事件，全局等到 `waitUntil`（至少 5 分钟，以 Retry-After 为准）。等待期间扫描不建任务、投递不领取、回填停止。

### 6. 拆半定位问题网址（恢复后同一批再次失败时）

- 触发条件：这一批是恢复后单独重推的被挡批次，并且再次返回 400/403/422。
- 开始时只给这一批的记录放宽重试上限：`maxAttempts = max(maxAttempts, attemptCount + 9)`（9 = ⌈log2 500⌉），写进审计。
- 把这批网址分成两半，每半单独发一次请求。第一层两半都失败：判定为整体配置问题（`global`），停止，总共只多发 2 次请求，记录全部保持被挡。只有一半失败：成功的一半记为已接受，失败的一半继续拆，一直拆到单个网址。定位到的问题网址记为"永久失败"，原因 `isolated_bad_url`，以后不再自动推。
- 子请求总数上限 `2 + 4 × ⌈log2 n⌉`（500 条为 38 次），超过则停（`probe_cap`）；任何一次子请求遇到 429、5xx、超时、网络错误或租约丢失则停（`interrupted`）。
- 拆分结束写一条 bisect 审计（结论 `local` / `global` / `interrupted` / `probe_cap`、子请求数、问题网址、已接受数、放宽的次数）。**熔断不自动关闭**：拆半产生的 4xx 本身就让它保持打开，必须人看过状态命令的输出后手动恢复。

### 7. 推送前整批校验

每批推送之前，对每一行逐项检查，不通过的行改为"已取消"、不进入本批，并记录脱敏后的诊断（`summarizeIndexNowValue`）：

- 网址格式：必须是 https、没有 query 与 fragment、没有双重编码、域名小写、没有默认端口、长度不超过 2048 → `url_invalid`；
- 网址域名必须等于站点设置里的 IndexNow host → `url_host_mismatch`；
- 文章仍然合格、canonical 没变 → `eligibility_failed`。

另外，扫描和投递在发请求之前都核对"站点设置里的 IndexNow host 等于 `SITE_URL` 的域名"，不一致按配置缺失处理（什么都不写）。原因：域名不一致是 422 最常见的原因，本地挡住既不花请求也不触发熔断。

### 8. 202 的语义

200 和 202 都算被接受（Owner 修改①；新域名的首批请求常返回 202）。202 的尝试记录的 `errorKind` 写 `key_validation_pending`，状态命令输出 `keyValidation`：最近一条被接受的尝试是 200 为 `verified`，是 202 为 `pending`，还没有则为 `none`，并给出 200 和 202 的条数（全部与最近 24 小时），回填每批的输出分别列出 `accepted200Urls` 和 `accepted202Urls`，出现 202 时提示"协议已接收，密钥验证待完成"。

### 9. 存量回填

- **候选**：按 id 游标翻页遍历全部已发布的小说文章，直到翻到**空页**才结束（不能用"本页不满"判断结束），已有任何出站记录的文章排除，其余逐篇复核资格。
- **回填按文章判重**：已有任何记录（任何状态、任何来源、任何修订号）的文章计入"已有记录"并跳过，不入队。数据库唯一键仍是 `url + revision`，不改，允许将来对实质更新再推；本单不新增更新推送入口。
- **清单**：`--expected-count` 必填，条数不一致时先写文件再报错退出（照 CPS）；`--count-only` 只数不写；`--article-ids` 严格校验（只能出现一次、不能有空项、必须是 UUID、不能重复；不存在、不在候选内、不合格的任何一项都整体拒绝）。`schema_version` 升为 2：新增 `--cutover-at` 与每条的 `published_at`，stats 给出切换前后的数量及按语种分布；apply 同时兼容 1 和 2。
- **执行**：一次可以跑完整份清单，内部每 500 条一批：入队 → 等这一批推完（每 10 秒查一次，超过 10 分钟报 `delivery_stalled`）→ 做全局检查 → 下一批。写模式要求 outbox 两项和 delivery 两项开关都在当前进程里打开。`--canary-locales` 按语种轮流取样做试推（确定性、每个语种内按 article_id 升序、余额补给其它语种），主推时已推过的会被"已有记录"规则自动跳过。
- **全局停止条件**（每批开始之前都做一次，第一批之前也做；全部用 SQL 聚合，不把行读进内存）：
  - (a) 熔断打开，即自上次恢复以来出现过任何一次 400/403/422（Owner 修改②，不再用"超过 3 条 422"）；
  - (b) 正在 429 等待；
  - (c) 全部回填记录里终态失败（永久失败 + 死信）超过 5%；
  - (d) 投递过回填记录的任务有失败的；
  - (e) 写模式从第二批起：上一批有不是"已接受 / 已取消"的记录（接受指 200 或 202）；最后一批之后也检查；
  - (f) 全站有任何死信；
  - (g) 全站有任何记录因 `url_invalid` 或 `url_host_mismatch` 被取消。

### 10. 恢复分三类

| 类别 | 处理方式 |
|---|---|
| 待重试（5xx、超时、网络错误、429 的退避） | 自动处理 |
| 熔断（400/403/422） | 人工执行恢复命令 |
| 死信（重试用尽） | 停机交给 Owner；原样重跑回填会跳过已有记录，不能代替重排 |

状态命令把死信行单独列出（网址、尝试次数、最后一次错误），并列出被取消的行数（按 `lastErrorKind`），`url_invalid` 与 `url_host_mismatch` 带网址明细。熔断打开时，状态命令列出触发那一批的全部网址并标出 `repeatAfterResume`。

### 11. 监控的三个口径

状态命令和回填的所有计数字段在字段名上写明单位，三个口径不相加：`urls`（网址数，出站记录行或尝试记录行）、`httpRequests`（HTTP 请求数，按不同的 `request_batch_id` 计）、`taskItems`（任务条目数，即 `GenericTaskItem` 的条数，批量投递任务和每分钟扫描任务分开统计）。不出现没有单位的 `count`、`completed` 等字段名。

## 三、对运行中推送的影响

- 旧格式的单条任务条目：新代码遇到直接跳过（`legacy_single_row_item`），任何表都不写；对应记录由下一批正常推出，不丢也不重复。
- 已有的待推、待重试、处理中记录原样被接手，处理中的照旧 35 分钟后自动恢复。
- 开关、白名单、写闸登记都不改；`indexnow_delivery` 仍只在轻量通道。
- 回滚只换镜像（无数据库改动）。**回滚前先关推送的两个开关，或确认待推积压为 0**，否则旧版本会按每次 1 个网址把积压推完。旧版本遇到新格式任务会判"载荷无效"失败，worker 失败告警会响，只是噪音；审计表里多出的控制事件对旧版本无影响。

## 四、已知限制与触发条件

| 项 | 现状 | 什么时候必须回头处理 |
|---|---|---|
| 死信记录重排工具 | 不做。重试 5 次都失败的记录不会被回填重推 | 死信数大于 0，交 Owner 决定是否做一个带审计的重排命令 |
| 控制状态查询的效率 | 每分钟扫描和每次领取各读一次；已用真实库用例固定了写法与执行计划 | 单次控制状态读取超过 50 毫秒（真实库用例的阈值），评估是否需要补索引（需要迁移，由 Owner 决定） |
| 网址变更后要不要再推 | 回填按文章判重，改 slug 后的新网址不会补推 | 公开网址解冻、开始允许改 slug 时重新评估 |
| 博客回填 | 不纳入（生产博客 0 篇；博客首次发布本来就写出站记录） | 出现开出站记录之前已发布的博客 |
| 每分钟只推 1 批 | 持续积压时吞吐上限是每分钟 500 个网址 | 待推积压持续 30 分钟以上不下降，改成每分钟多批 |
| 拆半对"单个网址"的判断 | 只剩 1 行就直接记为问题网址，无法与"整体配置问题"区分 | 出现单行批次的拆半结论时，人工核对状态命令的输出再恢复 |

## 附录：术语表

| 说法 | 含义 | 代码里的名字 |
|---|---|---|
| 出站记录 / 待推记录 | 一个要推的网址 | `indexnow_outbox` 表的一行 |
| 推送记录 / 尝试 | 一个网址的一次推送 | `indexnow_outbox_attempt` 表的一行 |
| 一批 | 一次 HTTP 请求里的一组网址，同批共用一个批号 | `request_batch_id`、`batch_size` |
| 批量投递任务 / 条目 | 后台任务框架里的工作单位，有租约；一个任务一个条目 | `GenericTask` / `GenericTaskItem`，类型 `indexnow_delivery`，条目类型 `indexnow_batch` |
| 每分钟扫描 | 每分钟一次的控制任务 | `indexnow.sweep.v1` |
| 熔断 | 遇到 400/403/422 后整体暂停，人工恢复 | 控制事件流 `breaker` |
| 被挡住（held） | 熔断期间退回待重试、立即到期但不领取的记录 | `retry_wait` 且 `last_http_status` 为 400/403/422 |
| 429 全局等待 | 对方限流后全局暂停到指定时间 | 控制事件流 `rate_limit` |
| 拆半 | 恢复后同一批再次失败时二分定位问题网址 | `indexnow.delivery.bisect` |
| 死信 | 重试 5 次都失败的记录 | 状态 `dead_letter` |
